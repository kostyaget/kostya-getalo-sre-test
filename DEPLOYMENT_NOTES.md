# Deployment Notes

Опиши тут своє рішення. Коротко, по кілька речень на пункт.

## Chosen architecture

Що підняв і чому саме так (сервіси, контейнери / процеси, де що живе).
------------------------------------------------------------------------
Docker Compose, 5 контейнеров: app, queue, nginx, mysql, redis.

Docker Compose — всё поднимается одной командой, работает независимо от 
среды (локально и на сервере одинаково).

nginx порт 80 наружу.

MySQL и Redis доступны только из докера (не открыты наружу).

app и queue — один образ, разные команды запуска, чтобы код не 
расходился по версиям.

## Server preparation

Як готував чистий VPS (користувачі, доступ, hardening, залежності, 
firewall).
-----------------------------------------------------------------------
создал обычного пользователя kastet с sudo, вместо работы от root.

сгенерировал SSH-ключ на своей машине, добавил публичный ключ в 
authorized_keys пользователя

отключил вход по паролю и вход под root напрямую (PermitRootLogin no, 
PasswordAuthentication no в sshd_config) - теперь зайти можно только по 
ключу и только под обычным пользователем для безопасности

Столкнулся с тем, что cloud-init (авто-настройка при создании VPS) 
добавляет свой отдельный файл 50-cloud-init.conf с 
PasswordAuthentication yes, который читается раньше основного конфига и 
перебивает мои настройки - SSH использует первое найденное значение 
параметра, поэтому мой запрет пароля игнорировался. Поменял значение 
прямо в этом файле.

Настроил firewall, открыто только ssh и порт80, все остальное закрыто 

Поставил fail2ban, защита от брутфорса, сталкивался с таким в работе.

## Deploy steps

Як задеплоїти застосунок з нуля. Кроки / команди.
---------------------------------------------------------------------------------------------------
Подготовить сервер (см. Server preparation — пользователь, SSH-ключ, firewall, Docker)

Клонировать репозиторий git clone git@github.com:.../repo.git

Создать .env в корне проекта на основе .env.example, заполнить пароли и APP_URL реальным IP

Собрать образы: docker compose build

Поднять базу и Redis отдельно, дождаться healthy!!!: docker compose up -d mysql redis

Сгенерировать APP_KEY: docker compose run --rm app php artisan key:generate --show, вписать в .env

Поднять весь стек: docker compose up -d

Проверить: curl http://IP/health, логи docker compose logs app

## How to redeploy

Як накотити нову версію. Що відбувається при повторному запуску.
-------------------------------------------------------------------------------------------------------

cd ~/sre-test
git pull
docker compose up -d --build

entrypoint.sh внутри контейнера app выполняется при каждом его запуске, заново прогоняет php artisan migrate --force и пересобирает кэш конфига/роутов. Если новых миграций нет то Laravel просто выводит "Nothing to migrate"

Докер смотрит что изменилось и пересобирает только это, там где измений не было ничего не проимходит 

во время теста rollback проверял этот сценарий, изменения применяются без потери volume



## Rollback approach

Як відкотитися на попередню версію, якщо деплой невдалий.
----------------------------------------------------------------------------------------------------------
Откат через git - на сервере в папке проекта 
git log --oneline -5

находим хэш нужного комита 
git reset --hard ХЭШ_КОММИТА - возвращамся к старой версии 
docker compose up -d --build - пересобираем контейнеры 

на правктике проверил по портил код, сайт упал, через тот же сценарий откатился на рабочую версию 

## What would be improved next

Чесно: що лишилось поза скоупом і що зробив би далі для реального проду.
-----------------------------------------------------------------------
Заметил, что nginx у меня подключает папку public/ напрямую с моего 
компьютера (через volume), а вот команда storage:link, которая должна 
создавать ссылку на папку с файлами, срабатывает только внутри 
контейнера app — то есть это как будто две разные папки, которые не 
видят друг друга. Прямо сейчас это не мешает, потому что в проекте нет 
загрузки файлов вообще. Но если бы она появилась — было бы круто это 
починить, чтобы оба контейнера смотрели в одно и то же место. По идее 
для этого нужно сделать общее хранилище (volume) между app и nginx, и 
чтобы app при старте сам туда копировал нужные файлы и делал symlink — 
тогда nginx бы видел актуальную версию, а не только то, что было на 
момент сборки образа


При финальной проверки кфг использовал ии, был обнаружен момент что пароль к MySQL передаётся как аргумент командной строки в healthcheck и backup-скрипте - mysql сам предупреждает об этом при каждом запуске как потом я обратил внимание. Сам бы не обратил внимания на это изза небольшого опыта, но это стоит исправить для реального прода, переносить пароль в защищённый конфиг-файл вместо командной строки.
